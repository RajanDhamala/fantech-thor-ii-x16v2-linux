## Verified observations

- Saved normally, stopped by the operator; capture is no longer active.
- 1,170,920 bytes; 11,485 USB records; 23.001303 seconds of packet timestamps. Capture-worker wall time was approximately 24.36 seconds.
- Device descriptor in frame 4 identifies VID/PID `30fa:1440`.
- Raw records include 6,235 control and 5,250 interrupt records. These are capture records, not counts of distinct Windows function calls.
- Feature-report traffic begins at about 8.498 seconds. Wireshark identifies GET_REPORT (frame 162) and SET_REPORT (frame 169), feature report ID 7, interface 1, requested length 8 bytes.
- Full-capture filtering in sharkd confirms 869 SET_REPORT setup records and 2 GET_REPORT setup records for `wValue=0x0307`.
- Frame 166 contains the recorded GET_REPORT response bytes `07 00 6c 09 17 00 03 2b`. No field meanings are assigned from this baseline alone.

## Candidate report-byte correlations

VirtualBox also records data-phase bytes in the header setup slot of separate control-stage records. Wireshark labels these as setup requests, so they must not be blindly treated as normal `usb.capdata`. The following adjacent records share an URB ID and an outgoing control endpoint:

| SET_REPORT setup frame | Candidate data frame | Bytes in the setup slot |
| --- | --- | --- |
| 169 | 171 | `07 18 03 00 01 00 23 00` |
| 176 | 178 | `07 18 09 00 01 00 00 00` |
| 183 | 185 | `07 18 00 00 01 00 00 00` |

This is consistent with the previously recovered report-07/command-18 family. The sequence is present during a recording whose notes say no Apply or settings changes. Mapping the burst specifically to opening the app is an inference from those notes; an exact UI event timestamp was not recorded. This does not establish the meaning of all command bytes, persistent memory writes, or a safe Linux replay.

## Coverage limits

7,036 records have captured lengths smaller than their original lengths. Some requested data survives in other control-stage records, but full original payload coverage is not established. Do not reconstruct missing response bytes or assume this recording is a complete USBPcap equivalent.

Analysis used installed `capinfos`, Wireshark `sharkd`, and a read-only Python parser with whole-file block validation and a matching SHA-256. REA packet inspection was attempted but its TShark provider is not configured. The companion JSON preserves selected decoder trees, full request correlations, counts, identity, and limitations. Source capture and metadata were not changed; no device commands were replayed.
